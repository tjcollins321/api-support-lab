## First offline revision

The agent's instructions and output-field descriptions now clarify that every
conditional or immediate information request belongs in both `missing` and the
reply. They name common canonical fields and explicitly include SDK version with
endpoint/model context for unfamiliar errors. Instructions also clarify parser
context, tentative interpretation of HTTP-success/parser failures, and concise
replies. No ticket IDs, expected labels, provenance, or evaluator data enter the
agent's input. The output is still generated by the model; no postprocessing fills
in answers or rewrites a reply to make it pass.

The T-010 evidence criterion changes separately from agent tuning. Escalation is
supported by a request for handling guidance, possible sensitivity, and absent
diagnostic payload. The organization's sector label alone does not establish that
reason. Scorer version **2** checks all three supporting facts, allowing alternative
verbatim ticket extracts within each group. It still rejects missing facts and
invented evidence. Categories, action, basis, severity, information requests,
retrieval, and transport-field boundaries remain unchanged.

This revision makes the frozen model outputs score **7/10 under scorer 2** rather
than the original 6/10. That one-point change is a scorer change, not improved
agent performance. The report itself is never overwritten. Reports now identify
the scorer version and a hash of expectations. Every new pass will also be scored
against the baseline expectations for comparison.

Offline verification passed **277 tests** with the network guard active, the API
key removed, and uv env-file loading/downloads disabled. Negative tests require
every handling fact and verbatim support; baseline tests verify the original
6/10 report and reviews remain unchanged during rescoring. This validates
software behavior, not agent performance.

## Authorized live cycles

The tuning checkpoint permitted up to ten cycles and reported $0.11 spent from a $15 allowance. This was an owner-reported budget checkpoint, not an inspection of account billing. The loop stopped after three cycles.

Each cycle attempts all ten tickets sequentially once, with `gpt-6.1-sol`, low
reasoning, eight turns per ticket, 4,096 output tokens per response, a 60-second
client timeout, zero client/runner retries, disabled tracing, and `store=False`.
No separate smoke requests or hidden retries are added. Operational failures,
available usage, hashes, settings, and versions remain saved. Unknown usage after
a failed attempt remains unknown cost; token estimates do not verify billing.

Before each cycle, preserve the source/rubric snapshots and hashes in a fresh
ignored directory. After each cycle, inspect redaction, all actual replies, and
grounding; record manual findings separately from automated agreement. Rescore
the reviewed copy offline, preserving originals. Any scorer change needs its own
rationale and negative tests; do not relax criteria to manufacture success.

Raw local runs and snapshots remain under ignored artifacts. No reply is sent or
account changed.

## Cycle 1

Cycle 1 returned **7/10 with scorer 2**, **6/10 with the original rubric**, and
no operational failures. All ten drafts were produced; eight passed qualitative
review. T-006 now retrieved the completion runbook, kept output exhaustion
inferred, classified the blocked report as high impact, and requested completion,
budget, parser/extraction context, and a sanitized excerpt. T-007 preserved the
unknown code and meaningfully asked for SDK version.

T-002 and T-008 omitted the required sanitized serialized schema request from
both fields and prose, failing follow-up completeness. T-004 used `request_info`
while providing supported conditional corrective guidance; its prose was useful,
but the predefined primary-action expectation still failed. These were retained,
with no score rewriting. The next instruction revision requires minimal schema
context when the serialized definition is absent and clarifies that supported
fixes can accompany supplementary questions.

Credential/pattern/settings checks and offline rescoring passed; original runs,
manual notes, settings/versions/usage, and hashes were preserved. The pass recorded
26 model responses with 48,472 input and 3,077 output tokens (51,549 total), including
25,731 cached input and 71 reasoning output tokens. At the previously checked
standard rates, known usage estimates to $0.0788251; this is not an inspected
billing charge. No API attempt failed in this cycle. Offline verification after
the second instruction revision again passed 277 tests before cycle 2.

These are tuning results on the same ten fixed tickets, with no held-out live
evaluation set. Improvements on these examples do not establish generalization.

## Cycle 2

Cycle 2 returned **9/10 with scorer 2**, **8/10 with the original rubric**, no
operational failures, and nine qualitative passes. Schema requests appeared in
both fields and prose, and the client timeout used the supported primary action.
T-005 alone failed: it treated an error/status not being handy as unavailable,
requested a generic diagnostic summary, and omitted collecting HTTP status and
concrete diagnostic field names. Its cause remained appropriately tentative.

The next revision explicitly distinguishes not-yet-collected metadata from
response fields that cannot exist because no response arrived. It requires
concrete canonical names for concrete questions and preserves minimal sanitized
handling summaries for sensitive-data routing. Four regression cases reject a
generic summary substituting for distinguishing fields and independently enforce
HTTP status, error code, and SDK-version requests. **281 offline tests passed**
before cycle 3, with the same network/env-file/key restrictions.

Cycle 2 recorded 25 model responses: 51,514 input, 3,206 output, and 54,720 total
tokens, including 27,061 cached input and 61 reasoning output tokens. Known-usage
standard-rate estimate: $0.0836721. Original results and reviews were retained,
redaction/settings/hash checks passed, and offline rescoring preserved every
record and finding.
